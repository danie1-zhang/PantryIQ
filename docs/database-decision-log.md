# Architecture Decision Log

This file records the main technical decisions for the pantry meal optimizer. It is meant to explain why the project is structured this way and to keep future changes consistent with the original plan.

# Product scope

The application should let a user:

- create an account and sign in
- manage foods in a personal pantry
- set nutrition targets for a meal
- generate a meal from available pantry items
- accept a meal or generate another option
- deduct an accepted meal from the pantry
- review previously accepted meals

Preference learning, external food APIs, background jobs, and an LLM interface can come later. The first goal is a reliable pantry-to-meal workflow.

# Application structure

The project will start as a modular monolith:

React + TypeScript
        |
        | HTTP/JSON
        v
FastAPI
        |
        | SQLAlchemy / psycopg
        v
PostgreSQL

Pantry management, authentication, optimization, and meal logging will remain modules in one backend rather than separate network services. They are closely related, and splitting them now would add deployment and debugging overhead without solving a current problem.

This does not rule out services later. A component should only be separated when there is a clear operational reason, such as independent scaling or a genuinely asynchronous workload.

# Frontend

The planned frontend stack is React, TypeScript, Vite, React Router, and TanStack Query.

- React provides the main interface.
- TypeScript keeps API payloads and UI state explicit.
- Vite is enough for this client-side application; server rendering is not currently needed.
- React Router will handle pages such as pantry, meal generation, history, and profile.
- TanStack Query will handle server state, including loading, errors, caching, and refreshes after pantry changes.

The frontend should not contain optimizer logic or connect directly to PostgreSQL. It should call the FastAPI backend.

# Backend

FastAPI is a natural fit because the optimizer is already written in Python. Pydantic will define and validate request and response bodies.

Routes should stay thin. A route is responsible for parsing a request, identifying the current user, calling application logic, and returning a response. Pantry updates, meal acceptance, and other business operations belong in services rather than large route functions.

SQLAlchemy models and Pydantic schemas serve different purposes and should remain separate:

- SQLAlchemy models describe stored rows and relationships.
- Request schemas define what clients may send.
- Response schemas define what the API may expose.

Database rows should not be returned automatically just because a column exists.

# Database stack

The database stack is PostgreSQL, SQLAlchemy 2, Alembic, and psycopg.

PostgreSQL fits the data because users, foods, pantry items, and meal logs have clear relationships. Foreign keys, check constraints, uniqueness rules, and transactions are useful here, especially when accepting a meal.

SQLAlchemy provides typed mappings, queries, relationships, sessions, and transaction handling without hiding the relational model. Raw SQL is still available for queries where it is clearer or performs better.

Alembic tracks schema changes. The normal workflow is:

1. Update the models.
2. Generate a migration.
3. Review the generated SQL and downgrade behavior.
4. Apply the migration.

Autogenerated migrations are a starting point, not something to apply without review.

Psycopg is the PostgreSQL driver used by SQLAlchemy. Application code should normally work through SQLAlchemy rather than calling the driver directly.

# Why not raw SQL or Supabase?

Raw SQL would provide more direct SQL practice, but it would also require more row mapping, repeated query code, and persistence plumbing. The project needs room for API, frontend, authentication, optimization, and deployment work. Raw SQL can still be used selectively.

Supabase would speed up hosting and authentication, but using its client directly from React would bypass much of the backend design this project is intended to explore. A managed PostgreSQL provider may still be used in production; FastAPI and SQLAlchemy will remain the application boundary.

# Initial schema

The first migration contains five tables:

```text
users
foods
pantry_items
meal_logs
meal_log_items
```

Recommendation history is deliberately excluded for now.

# Users

`users` stores account information, optional profile fields, and default nutrition goals.

Important rules:

- IDs are UUIDs.
- Email and username are unique.
- Only a password hash is stored.
- Age, height, weight, and gender are optional.
- Nutrition goals cannot be negative.
- Sodium and sugar maximums are optional.

Keeping one set of goals on the user is sufficient for the initial version. If workout-day, rest-day, or other reusable profiles are needed, they can move to a separate table later.

# Foods

`foods` replaces the CSV catalog as the application's source of truth. It stores the serving definition and nutrition values for one food or product.

`external_source` and `external_id` link a record back to imported data when available. Their combination is unique. Names are not unique because different brands and serving definitions may use the same name.

Serving size, nutrition values, and cost must be nonnegative. Cost is optional.

# Pantry items

`pantry_items` represents a user's inventory. One row means that one user has a quantity of one food.

There is no separate table for each pantry and no `pantries` table yet. A user's pantry is simply the set of pantry rows with that `user_id`.

The `(user_id, food_id)` pair is unique. Adding more of an existing food updates its quantity instead of creating another row. If expiration batches become important, this constraint can be revisited and batches can be modeled separately.

Available servings and the per-meal limit cannot be negative. The per-meal limit also cannot exceed the available quantity.

# Meal logs

`meal_logs` stores accepted meals. Each log belongs to one user and records when the meal was eaten, total nutrition, an optional rating, and optional notes.

Nutrition totals are stored rather than recalculated from the current catalog. That keeps history stable if a food record is corrected later. Ratings, when present, are limited to 1 through 5.

# Meal log items

`meal_log_items` stores the foods in an accepted meal. Each row references a meal log and the source food, and records the number of servings.

The food name and per-serving nutrition values are copied into snapshot columns at acceptance time. These snapshots keep the historical meal accurate even if the food catalog changes.

# Relationships and deletion behavior

```text
users 1 ---- many pantry_items many ---- 1 foods
users 1 ---- many meal_logs
meal_logs 1 ---- many meal_log_items many ---- 1 foods
```

Deleting a user removes that user's pantry items and meal logs. Deleting a meal log removes its items. Foods referenced by pantry or meal-history records are restricted from deletion so those records cannot be left pointing at nothing.

All tables use timezone-aware `created_at` and `updated_at` values. `meal_logs.eaten_at` is timezone-aware as well.

# Food catalog import

The existing `data/food_catalog.csv` seeds the `foods` table. The importer splits values such as `4 oz` into numeric serving size and serving unit, then inserts or updates foods using their external source and ID.

The current CSV does not have a brand column, so imported rows use `Generic`. This is explicit rather than pretending the source contains brand data that it does not.

External food search can be added after the core workflow is stable. Likely sources include USDA FoodData Central and Open Food Facts. Selected results should be normalized and stored locally rather than importing an entire external database upfront.

# Pantry and meal flow

When the pantry page loads, the backend queries pantry items for the authenticated user and joins their food records for nutrition details.

When a food is added, the backend checks whether that user already has the food. It either increments the existing quantity or creates a pantry item.

For meal generation, the backend loads available pantry items and converts them into the optimizer's input format. Reusing a pandas DataFrame initially is acceptable because it avoids rewriting the existing optimizer at the same time as the persistence layer. Typed objects can replace that adapter later.

A generated meal must respect inventory and per-meal serving limits. It should also follow basic structure rules, including a meaningful protein source, a carbohydrate or produce item, reasonable condiment use, and limits on total foods and servings.

The current scoring approach treats:

- calories, carbohydrates, and fat as targets
- protein as a minimum without an excess penalty
- sodium and sugar as optional maximums
- cost as an optional preference

Feasible meals always rank ahead of infeasible meals. If none are feasible, the optimizer may return the best near-feasible result with a clear warning.

# Accepting a meal

Meal acceptance must happen in one database transaction:

1. Verify that each pantry item still has enough servings.
2. Deduct every serving amount.
3. Mark depleted items unavailable.
4. Create the meal log.
5. Create its snapshot items.
6. Commit.

If any step fails, the transaction rolls back. Pantry deductions and meal history must never disagree because only part of the operation succeeded.

# Recommendation storage

Generated recommendations are temporary in the first version. Regenerating discards the previous result; accepting creates a meal log.

This keeps the initial flow small, but it means page refreshes can lose a recommendation and rejected meals are not available for analytics. When rejection analysis or preference learning becomes useful, `meal_recommendations` and `meal_recommendation_items` can be added in a later migration.

# Sessions

FastAPI will use one SQLAlchemy session per request. The session is opened at the request boundary and always closed afterward. Application code decides where to commit or roll back; mutable sessions are never shared between concurrent requests.

# Authentication and authorization

Authentication comes after the pantry and meal flows. Registration will hash passwords before storing them. Login will verify the hash and issue signed tokens.

Protected routes must determine `user_id` from the verified identity. The frontend must not be allowed to select another user's ID in a pantry or meal request.

# Configuration and secrets

Local configuration lives in `.env`, which is ignored by Git. A committed `.env.example` may document required variable names using placeholder values.

Expected configuration will eventually include:

```text
DATABASE_URL
JWT_SECRET_KEY
USDA_API_KEY
RABBITMQ_URL
```

Production secrets belong in the deployment platform's secret manager, not in the repository.

# Docker and background work

Docker will be added after the database and API work normally outside containers. Docker Compose can eventually run the frontend, backend, PostgreSQL, RabbitMQ, and a worker together.

RabbitMQ is not needed for pantry CRUD or the first synchronous optimizer endpoint. It becomes useful for work that does not need to finish during an HTTP request, such as analytics, expiration notifications, large imports, or preference updates. Celery is the likely first worker framework because it already provides task execution and retry behavior.

An accepted-meal event should only be published after the database transaction commits. Publishing before commit could trigger work for a meal that was later rolled back.

# Build order

1. PostgreSQL models, sessions, migration, and CSV seed script.
2. Food search and pantry CRUD endpoints.
3. Optimizer integration and transactional meal acceptance.
4. Pantry, meal generation, and history screens.
5. Registration, password hashing, and token authentication.
6. Docker and local service orchestration.
7. RabbitMQ and the first justified background task.

This order keeps each stage testable and avoids adding infrastructure before there is a feature that needs it.
